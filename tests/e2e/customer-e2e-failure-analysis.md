# 客户通话 E2E 失败归因与修改方案（2026-10-21）

基线：SDK `dev` 提交 `c9063dfe` 构建后，116 项真实账号 E2E 中 73 通过、42 失败、1 因同组前项失败而跳过。运行时清空四个已过期的 Token 环境变量，使用已配置密码换取新 Token；没有改动凭据文件。以下按**失败的 Playwright test 数**统计，同一前置条件可造成多项失败，不代表同样数量的独立产品缺陷。原始逐项 JSON 已另存为本机忽略目录中的 `test-results/baseline-2026-10-21.json`；其中可能包含真实账号运行数据，不纳入 Git。

2026-10-22 重新核对多设备环境：E2E 原先只传了随机 `deviceId`，`demo/callkit/call-demo.tsx` 未设置 `isFixedDeviceId`，Provider 因此向 SDK 传 `useFixedDeviceId: true`。现由测试 URL 指定 `useFixedDeviceId=false`，demo 通过 `isFixedDeviceId: false` 传入 Provider，Provider 再传到 SDK；不再额外指定 `deviceId`，与 `../websdk2/demo` 的初始化方式一致。测试登录后也核对 Provider 配置值。另发现当前终端预置的 `EASEMOB_APPKEY=easemob#dutest01` 与账号 `du003/du004` 覆盖了项目 `.env.e2e.local` 的 `easemob-demo#session-sync-prod` 与 `zd1/zd2`。旧环境下即使两端分别生成不同的 `webim_random_web_...` 资源，B2 登录后 B1 仍收到 `206`；同浏览器双 tab 也复现。清除终端覆盖值、使用项目环境后，双 tab 并存前置检查与 `C-01/C-02/C-05` 均通过。因此原先“15 项因多端会话前置不成立”的归因仅适用于旧运行环境，不能代表当前项目环境或 SDK 参数效果。

按项目环境复跑原先 15 项：首轮 8 通过、7 失败（`test-results/multidevice-fifteen-local-env-2026-10-22.json`）。`MD-08` 与多设备 `OFF-03` 只是重连后查询早于 Fusion 可用；改为等待公开快照接口可用，原业务断言均聚焦通过。当前为 **10 项通过，5 项仍失败／波动**：`C-03/C-04` 拒绝与忙线 2 项中 B2 收到 `ended`，但没有用例要求的 `onHandledOnOtherDevice`；`MD-06` 会议与一对一 2 项中非有效设备的 `joinCall`／`hangup` 返回成功，需 SDK／服务端核查有效设备权限；CallKit `MD-04` 同时接听聚焦 3 轮 1 通过、2 失败，失败时服务端快照仅一台 B 设备为 `accepted`，两台 B 的 CallService 都回到空闲，日志含 RTC `OPERATION_ABORTED`，需沿获胜设备的信令和 RTC 清理顺序取证。`MD-01/02/03`、`MD-05/07`、`C-01/02/05`、`C-06` 等通过项不再归为登录环境失败。

2026-10-22 聚焦复核了 `C-01/C-02/C-05` 组合用例的登录前置，分别使用显式不同的 `deviceId` 和 `useFixedDeviceId: false`，两次仍在 B2 登录后收到 B1 的 `206` 断线；本次没有重跑全部 15 项。

同日定点重跑“仍需取证”的 6 项，第一轮 2 通过、4 失败；对第一轮通过的 `OFF-03` 已取消邀请和 `WN-03 hangup` 请求未到达各追加 2 轮。`OFF-03` 总计 2 通过、1 失败：追加轮次的失败位于 A 取消后等待服务端快照变为 `ended`，与基线中创建快照超时的位置不同，尚未运行到 B 登录后的断言。`WN-03 hangup` 请求未到达总计 1 通过、2 失败，失败时服务端快照为 `ended` 而用例预期 `open`。其余 4 项接听／取消响应超时均与基线相同，仍在 900 ms 后要求原按钮可见的断言处失败。逐项结果保存在本机忽略目录的 `test-results/targeted-six-2026-10-22.json` 和 `test-results/targeted-two-repeat-2026-10-22.json`。这次只重跑，没有改用例或产品代码。

随后给这 6 项加了仅在测试浏览器生效的时间线日志，保留原断言，记录 SDK 公共方法、故障注入、信令通知、CallKit 服务入口、RTC 远端离开和界面状态。`test-results/artifacts/` 下每端的 `*-call-trace.json` 是逐项原始证据；对应运行结果为 `trace-six-2026-10-22.json`、`trace-off-hangup-repeat-2026-10-22.json` 和 `trace-hangup-path-2026-10-22.json`。

- `OFF-03` 追加 3 轮中 1 通过、2 失败。两个失败轮次里 `cancelCall` 均返回 `ended/canceled`，但取消点击后立即发起的首次 `getCallSnapshot` Promise 持续未完成，15 秒断言超时；失败清理阶段重新查询立即返回 `ended/canceled`。这次的失败点是并发取消／查询的响应悬挂或脚手架轮询时机，尚未进入 B 离线补来电检查；需在 SDK 请求层核对该首次查询为何未完成。
- `WN-03 acceptCall` 请求未到达：B 点击后约 20 毫秒接听按钮消失，700 毫秒后注入超时；随后查询仍为 `open`，B 仍 `ringing`，直至服务端正常超时。CallKit 在请求确认前关闭了来电通知，且错误后未恢复。
- `WN-03 cancelCall` 请求未到达：A 点击后约 25 毫秒挂断按钮消失，700 毫秒后注入超时；此时快照仍为 `open`，服务端稍后才正常超时。CallKit 在取消确认前清了呼叫界面。
- `WN-03 acceptCall/cancelCall` 服务端已处理：原始 SDK 请求分别在约 28／26 毫秒内成功，服务端快照分别为已接听／已取消，注入的错误在约 700 毫秒后才抛出。当前 900 毫秒后仍要求旧按钮可见的断言不区分成功状态已经到达的情况；应按权威状态到达前后分别观察，但保留“超时不本地编造结果”的规范要求。
- `WN-03 hangup` 请求未到达：A 的信令 `hangup` 被注入拦住，但本地立即退出 RTC；B 收到 RTC `user-left/Quit`，`CallService.handleUserLeft` 发起真实 `hangup`，服务端返回 `ended/hangup`。单独复跑的服务入口调用栈确认了这条路径。故当前注入不能模拟“双方都未处理挂断”；CallKit 的立即退出 RTC／清界面也与超时待定要求冲突。测试注入需同时控制 RTC 离会的时机或在更底层模拟无响应，不可删掉规范断言。

随后按上述证据修正 CallKit：接听响应不确定时查询快照，只有确认已接听才加入 RTC；接听失败时保留来电通知。取消／挂断响应不确定时先查询快照，若呼叫仍在则保留原通话与 RTC 并抛出错误供界面显示，只有确认结束后才清理。CallKit 挂断按钮等待服务结果，不再点击即清界面或立即退出 RTC。服务层 44 个单测通过，`WN-03` 六个变体在修正用例间清理后连续运行全部通过（`test-results/wn03-six-after-cleanup-2026-10-22.json`）。

`OFF-03` 再次复现取消已成功而并发 `getCallSnapshot` 悬挂；首次查询 Promise 超过 15 秒未完成，稍后重新查询得到 `ended/canceled`。其业务步骤要求 A 先完成取消，再让 B 登录取离线邀请，因此用例现等待 A 恢复空闲后才查询服务端快照，未删减快照或 B 端无来电断言；重复 3 轮全部通过（`test-results/off03-after-sequencing-2026-10-22.json`）。并发取消／查询时首次查询悬挂仍是待追查的 SDK 请求响应问题，不能将用例稳定通过视为该问题已解决。

同日修正 7 项测试的等待／通知定位并聚焦复跑：`OFF-04`、`RC-01`、`RC-02` 三个分支共 5 项通过，`RTC-01` 通过；`DEV-01` 仍失败。进一步验证发现，原测试浏览器的自动授权参数使 `grantPermissions([])` 无法模拟拒绝：摄像头、麦克风和 `getUserMedia` 均显示已授权。改为独立浏览器且从建上下文起拒绝媒体权限后，`getUserMedia` 确实返回 `NotAllowedError`，但 CallKit 未显示权限错误提示，主叫仍在 `Connecting...`。用户随后决定当前自动授权环境不验收权限流，`DEV-01` 已移除；这次拒权观测保留为历史记录，不纳入当前环境的通过统计。

用户确认 `ISO-01` 应以现有 CallKit 发送文本呼叫记录为准；用例已改为核对主叫会话中本次通话的文本记录、扩展字段和唯一性，聚焦复跑通过。`RACE-01` 追加邀请复核时发现双击产生 2 次 SDK 请求，但服务端成员仅 1 条、C 端来电仅 1 次；demo 增加同步防重复保护后，三个数量均为 1，聚焦复跑通过。`1V1-06` 已占线第二通聚焦复跑仍失败：第二通创建成功，B 对其报忙被本地通话槽以 `110` 拒绝。

## 建议实施顺序
