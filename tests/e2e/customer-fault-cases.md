# 客户通话规范：可控故障执行用例

本文件记录需要代理、服务端注入或多设备实验室才能可靠复现的场景。它们不能由普通 `setOffline()`、等待固定时间或伪造 SDK 成功响应代替。每条独立运行，记录注入点、损伤方式、开始／结束时间、操作请求次数、各端 UI／回调，以及网络恢复后各在线端的服务端快照。每条结束时清理通话并验证账号可再拨。

| 编号 | 必须具备的注入能力与执行步骤 | 观察端与通过条件 |
| --- | --- | --- |
| OFF-06 | 离线队列至少一页有两条邀请；让 B 查询其中一条通话快照时网络失败，保留服务端队列和游标。恢复网络后重新同步该页。 | B 不能把失败页当作已处理；有效邀请最终只显示一次，已失效邀请不显示，游标不倒退。A 与 B 恢复后快照一致。记录失败条目、页号和重拉次数。 |
| RC-03 | 一种执行：B 振铃中断线，B2 接走；另一种执行：B 在会议中断线期间服务端已把 B 标为离开。B 恢复并完成呼叫就绪。 | B 先查快照，不恢复媒体也不结束仍在进行的服务端通话；B2／其他留会成员继续原通话。核对 B 账号的设备或状态与快照一致。 |
| RC-04 | B 持有一通已接通通话，重连后让自动 `getCallSnapshot` 及其一次重试连续失败；之后恢复查询。 | 失败期间 B 不发布／恢复媒体、不显示结束提示、不把本地写成已结束。成功查询后的服务端结果决定继续、结束或本机退出。记录两次失败与恢复查询时间。 |
| RC-05 | B 是原通话有效设备；分开执行自动恢复动作失败和用户主动点击恢复失败，故障不改变服务端通话。 | 自动失败：本机退出本次界面并明确提示恢复失败；主动失败：只提示本次失败，不额外清除可查询通话。两次的服务端快照仍进行中，通话 ID 与时间不变。 |
| RC-06 | 在新连接可用但呼叫通道尚未就绪的窗口，尝试接听及离线同步，并注入一条异常呼叫推送；之后完成就绪。 | 窗口内没有呼叫业务请求，异常推送不振铃、不更改本地通话；就绪后服务端快照不包含推送制造的假状态。记录网络连接和呼叫就绪的各自时间。 |
| WN-01 | 代理拦截 A 第一次 `createCall`，确认请求在到达业务处理前失败；在截止时间内允许 SDK 以同一逻辑请求重试一次。 | A、B 最终只有一个通话 ID、B 只收到一次来电，快照与正常创建相同。记录两次传输尝试、一次业务处理和重试时间。 |
| WN-02 | 代理让创建或接听收到一次明确业务失败，而非网络错误；记录 SDK 发出的请求次数。 | 不自动再次请求。创建失败时无新通话；接听失败时参与者仍是失败前待接听／振铃状态。A、B 查询快照核对。 |
| WN-03 | 对接听、取消、挂断分别执行“请求已处理但响应丢失”和“请求未到达业务处理”，使发起端等待到超时；恢复后各端查快照。 | 超时当下界面不编造拒绝、忙线、取消或挂断终态。已处理则按服务端结果收敛；未处理则回到原状态并可重试。浏览器 `callkit.spec.ts` 已有公开 API 响应边界版，仍需代理传输层版。 |
| WN-04 | 三人会议中连续接听、离开、追加邀请；代理向 B 丢弃一条成员变更通知或提供不完整结果，随后允许全量同步。 | B 在补齐前不展示半份成员列表；补齐后成员状态、设备和时间与 A、C 的服务端快照一致。SDK 公开快照没有 `revision`，需记录代理／服务端层的版本证据。 |
| WN-05 | 已接通并记录创建、接通、接听时间；代理造成真实心跳超时，随后恢复连接和呼叫就绪。 | 本机仍有效时恢复原通话，三个时间和设备不变；恢复完成前不提前发布媒体。普通短暂 WebSocket 断链不能代替心跳超时。 |

`RC-03～06`、`WN-01、02、04、05`、`OFF-06` 尚未加入可重复运行的 Playwright 故障注入脚本。执行这些编号前，应先准备与真实业务服务相连的可控代理或等效实验室条件，并把注入命中证据保存为测试附件；否则记录“未执行”，不把邻近场景折算为通过。
