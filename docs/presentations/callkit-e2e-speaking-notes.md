# CallKit E2E 测试分享｜讲述提示

总时长约 12 分钟。演示前可打开 `callkit-e2e-sharing.pptx`，在 Keynote 中直接播放或另存为 `.key`。

## 1. 把通话测到真的听见、真的看见（0.5 分钟）

今天分享的是这套 CallKit E2E 测试的思路。它覆盖信令、同账号多设备、CallKit 界面和真实 RTC 媒体。重点是验证“远端确实收到了什么”。

## 2. 一次通话成功意味着什么（1 分钟）

手工看见接听按钮消失，并不能说明服务端状态、设备归属和媒体都正确。比如同账号两台设备中，败者也可能误入 RTC；UI 进入通话，远端也可能黑屏。这四层需要交叉验证。

## 3. 一套用例串起真实链路（1.5 分钟）

Playwright 打开独立浏览器上下文，扮演 A、B、C。每端用不同 deviceId，避免同账号多端互踢。操作走真实 IM、呼叫信令和 RTC。断言分别读取服务端快照、页面状态、运行 trace 与媒体附件。测试输入是可控的，链路仍是真实的。

## 4. 真实视频（2 分钟）

视频测试不只是看 `<video>` 是否存在。发送端把动态 Canvas 转成视频轨并替换已发布轨；接收端从远端 video 采样像素，同时检查解码帧数持续增加。三人会议分别发红、绿、蓝，验证六条有向接收链路，再轮换颜色。这样能抓到黑屏、画面串到错误的人，以及停在旧帧。失败附件保存接收端 PNG、颜色比例和轨道 ID。

## 5. 真实语音（2 分钟）

主叫播放固定中文句子进入通话。被叫录制的是收到的远端音轨，保存 WAV，交给本地 ASR 识别。用顺序匹配判断识别文本与原句是否接近，并容忍简繁差异。这个验证比麦克风图标或音量条更接近用户实际听见的结果。ASR 有波动，所以保留音频与转写，便于回听。

## 6. 复杂场景（1.5 分钟）

同账号多端要看参与者的 deviceUuid 是否指向真正接听的设备。响应超时分请求未到达和服务端已处理两类；同样的客户端错误提示可能对应不同服务端终态。成员掉线、视频发送中断恢复后，还要检查其他成员是否仍正常通话和接收媒体。

## 7. 相比手工测试的价值（2 分钟）

手工测试适合真实硬件体验和主观感受，但多人配合、竞态时机和重复回归成本高。自动化把时序固定下来，并把“看到了什么”变成远端像素、视频帧、录音和转写。失败时同步留下快照与 trace，更容易重现和归因。这里强调的是可重复性与证据质量，不报未经统计的节省比例。

## 8. 一次排障实例（1 分钟）

WN-03 是接听响应超时场景。仅看 UI 容易把失败归为超时处理；结合服务端快照和 trace，能发现更早出现的 busy 1704，再判断是环境前置状态、SDK/CallKit 行为还是超时分支自身的问题。自动化的价值不只是一条红绿结果，还包括定位线索。

## 9. 总结（0.5–1 分钟）

这套测试最终要证明三件事：服务端与 UI 的状态正确；同账号多端的设备归属正确；远端收到的媒体内容正确。后续继续把环境就绪检查和失败归因沉淀进回归流程。
